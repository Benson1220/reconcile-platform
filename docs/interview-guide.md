# 面試展示與回答指南

## 先理解作品定位

名稱：跨系統對帳與異常追查平台。
定位：用訂單、付款、結算的合成資料，展示資料整合、確定性比對、證據追溯與案件處理流程的本機原型。

三十秒開場，可以先讀懂再用自己的話說：

> 我做了一個跨系統對帳平台，處理訂單、付款與結算資料對不起來時的追查流程。
> 系統會驗證 CSV、用四條規則找出異常，保存原始證據，讓使用者記錄調查、備註與結案。
> 我特別處理重複匯入、資料完整涵蓋日期、金額精度與多分頁更新衝突。
> 目前使用本機規則式摘要，方便穩定展示，不需要外部模型額度。

## 第 2 步：照五分鐘流程演練

| 時間 | 操作 | 要說明的重點 |
|---|---|---|
| 0:00–0:30 | 開啟首頁，說明情境 | 客服接到已付款但訂單未更新的問題，IT 需要跨系統找證據 |
| 0:30–1:20 | 上傳三份範例 CSV | 欄位驗證、固定基準時間、四條規則；相同資料沿用批次 |
| 1:20–2:10 | 開 O1004，看結算證據 | 2000 − 40 = 1960，來源記成 1970；列號、檔案與精確差額 |
| 2:10–3:00 | 開 O1003，看缺漏證據 | 預期日期、完整涵蓋範圍、零筆搜尋結果；查無不等於未入帳 |
| 3:00–4:00 | 在一筆案件加「展示練習」備註並更新狀態 | 歷程、結案說明、版本檢查；保留原始證據 |
| 4:00–4:30 | 開啟規則式摘要並點 E1／E2 | 事實與查核步驟有明確依據，摘要不自動修正資料 |
| 4:30–5:00 | 指向測試與架構文件 | 115 項測試；說明一個技術取捨與目前限制 |

每次演練新增的備註會保留。用「展示練習」標記，避免把練習內容當成真實處理結果。
如果案件已結案，可新增補充備註，或用明確原因重新調查，不必刪除或重置資料。

## 第 3 步：選一個失敗情境補充展示

五分鐘主流程熟悉後，再準備其中一個，面試官追問時使用：

### A. 重複匯入

再次上傳相同三份 CSV，沿用相同設定。
預期 reused=true，案件仍四筆，既有狀態與備註保留。
解釋檔案 SHA-256、設定雜湊、規則版本、唯一約束與交易的分工。

### B. 資料涵蓋不足

將上傳設定中的「結算資料完整涵蓋至」改成 2026-11-15，使用同一組範例 CSV。
預期顯示資料不足，不儲存新批次。展示後把日期還原為 2026-11-16。
解釋資料缺漏與資料尚未取得，是不同狀況。

### C. 多分頁更新衝突

兩個分頁打開同一案件。
第一個分頁先新增一筆備註；第二個分頁仍用舊版本儲存時會收到 409。
第二個分頁使用「重新載入案件，保留草稿」，核對最新紀錄後再儲存。
說明 expected_version 與資料庫列鎖如何避免覆蓋進度。

## 第 4 步：準備可據實回答的技術問題

| 問題 | 回答方向 | 可以打開的程式 |
|---|---|---|
| 為何金額用 Decimal？ | 從 CSV 字串轉為十進位，資料庫用 NUMERIC(18,2)；一分錢差額也要精確 | app/reconciliation.py 的 parse_money |
| 如何避免重複案件？ | 來源快照指紋、設定雜湊、規則版本與唯一鍵；相同輸入沿用批次 | app/database.py 的 save_snapshot |
| 匯入一半失敗怎麼辦？ | 來源與結果用同一交易，有錯誤整次回復；測試故意讓證據連結失敗 | tests/test_database.py |
| 為何保留原始 CSV？ | 保留位元組、雜湊、原始列與型別化資料，方便追溯與重新分析 | sql/001_initial.sql |
| 如何證明沒有結算？ | 保存搜尋付款編號、符合筆數、掃描數與來源完整性宣告；仍不是資金流向證明 | app/reconciliation.py 的 find_missing_settlements |
| 結案後為何還有四筆異常？ | 比對結果是歷史事實，結案是人工處理狀態，兩者分開保存 | cases.payload、cases.status、case_events |
| 多人更新如何處理？ | 交易內 SELECT FOR UPDATE，再檢查 expected_version；舊版回 409 | app/database.py 的 update_case |
| 為何摘要先用規則？ | 目前四種異常可明確定義，模板可重現、無外部費用；新增類型需新增範本 | app/rule_summary.py |
| 有真的整合 AI 嗎？ | 有 API 串接與模擬測試；尚未成功驗證實際模型摘要，目前付費入口停用 | app/ai_summary.py、tests/test_ai_summary.py |
| 測試會動到我的案件嗎？ | 整合測試使用獨立隨機 schema，完成後只清除該 schema | tests/test_api_database.py 等 |

不要只背回答。先找到對應函式，練習用一筆資料解釋它如何執行。

## 目前限制與下一步

- 合成資料與本機展示，尚未串接真實 ERP、付款平台或銀行。
- 單一 TWD、每張訂單最多一筆成功付款，尚未支援退款、分期與多筆拆帳。
- 結算完整性由來源設定宣告，尚未串接批次清單驗證。
- 同步處理小批量上傳；尚無大規模壓力測試、背景工作與正式監控。
- 尚未登入、權限分級與經驗證的操作人身分；目前只綁定本機使用。
- 不同批次的案件不自動合併處理進度。

面試時選一個限制說明後續設計即可，例如登入權限、工作佇列或來源批次清單，不必聲稱已完成。
