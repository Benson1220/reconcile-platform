# 本機規則式摘要：整理異常、證據與查核步驟

## 目前完成

已將首頁摘要區改成「規則式查核摘要」。它使用固定範本與原始證據，在本機計算與組合文字。
不呼叫 OpenAI、不使用 API 額度，不需要模型金鑰或新增套件。
付費 AI 產生預設停用，舊頁面或舊 API 的產生要求會收到 403，避免誤觸模型呼叫。

保持原本的後端與 PostgreSQL 執行。這台電腦的 migration 4 已套用，不必重新匯入 CSV。

如果仍沒有新畫面，可在原本啟動後端的終端機按 Control+C，再執行：

## 第 2 步：打開摘要（瀏覽器操作）

在 O1004 那一列按「查看證據」，往下找到「規則式查核摘要」。
按「產生規則式摘要」。不會要求金鑰，也不會前往外部網站。
摘要若已產生，會直接顯示；按鈕變成「讀取目前版本摘要」。
我們已透過本機 API 驗證四種摘要，因此原批次可能已顯示保存結果，這是正常的。

O1004 的概述應包括：

> 結算 S8004：2000.00 − 40.00 應為 1960.00，紀錄淨額為 1970.00，偏高 10.00 TWD。

這些數字從該案件的原始結算證據讀取與計算，不是把範例答案寫死。

## 第 3 步：閱讀摘要區塊（瀏覽器操作）

| 區塊 | 內容 |
|---|---|
| 概述 | 異常類型、關聯編號與差異 |
| 證據重點 | 從原始列或查無紀錄條件整理的事實 |
| 建議查核步驟 | 對應該規則的固定人工查核清單 |
| 尚缺資料 | 還需向系統或資料提供方取得的確認依據 |

本機摘要不推測已確認根因，不會生成額外的未驗證原因。
例如 O1004 會建議核對原始結算欄位、費用與淨額定義，以及處理後的驗證紀錄。
這些是「接下來要查的事」，不是宣稱你已完成修正。

## 第 4 步：點證據引用（瀏覽器操作）

點 E1／E2 引用按鈕，會捲動到原始證據卡片。
O1004 可確認 settlements.csv 第 4 列與 payments.csv 第 5 列。
E1／E2 是該案件內的證據編號，其他案件可能對應不同來源。

## 第 5 步：查看其他三種摘要（瀏覽器操作）

關閉側欄，再依序打開 O1001、O1002、O1003：

| 案件 | 摘要重點 | 建議查核方向 |
|---|---|---|
| O1001 | 成功付款與未付款訂單快照不一致 | 時間範圍、付款通知、重試與訂單更新日誌 |
| O1002 | 訂單 1500、付款 1400，差額 -100 | 付款當時訂單版本、價格異動與業務情境 |
| O1003 | P9003 在已涵蓋的結算資料中符合筆數為 0 | 來源批次完整性、原始結算明細與延後結算說明 |

O1003 摘要會明確保留完整涵蓋日期與比對基準時間，並說明「查無紀錄」不代表已證明資金未入帳。

## 第 6 步：確認保存與舊版提示

重新整理後，摘要會從本機 PostgreSQL 讀回。
同一案件版本、同一摘要規則版本與相同輸入會沿用保存結果。
案件新增備註或狀態改變後，舊摘要會標示版本過期；點「依最新案件產生摘要」可本機重建。
摘要本身不會修改案件狀態、備註或原始證據。

## 閱讀說明，不需貼上或單獨執行

| 檔案 | 用途 |
|---|---|
| app/rule_summary.py | 四種摘要範本、原始證據對應、Decimal 金額計算與保存 |
| sql/004_rule_summaries.sql | 獨立保存規則式摘要，不混入歷史 AI 摘要 |
| app/api.py | 本機摘要模式、讀取與產生 API |
| app/web/app.js | 規則式摘要按鈕、內容、引用與版本提示 |

API：

- GET /api/summary/status：回傳 mode=rules、requires_api_key=false、external_requests=false。
- GET /api/cases/{case_id}/rule-summary：讀取保存的規則式摘要。
- POST /api/cases/{case_id}/rule-summary：本機產生或沿用摘要。

既有 AI 程式與歷史結果保留，但外部產生功能由 OPENAI_SUMMARY_ENABLED 控制，預設 false。
目前首頁完全不呼叫 /api/ai/status 或 /ai-summary；即使 .env 留有金鑰，也不會因本機摘要而使用它。
日後若要恢復外部模型，應另行確認啟用方式與使用費用。

這是固定規則系統，不會理解任意新異常；新增異常類型時，要新增對應範本。
